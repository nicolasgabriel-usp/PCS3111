Aula: Persistência de Objetos em C++
1. A ideia central

Objetos vivem na memória e somem quando o programa termina. Persistir é gravar o estado do objeto (seus atributos) em um arquivo para recriá-lo depois. Não gravamos o objeto em si, só os dados necessários para reconstruí-lo.

No exercício, o estado de um Jogador que importa é nome, hpMax e forca. O hp não é salvo porque o construtor o inicializa com hpMax.

Criamos uma classe separada (PersistenciaDeJogador) para não misturar a lógica de arquivo com a lógica do jogo. Cada classe tem uma responsabilidade só.

2. Streams de arquivo
Classe	Uso	Header
ofstream	escrever (output)	<fstream>
ifstream	ler (input)	<fstream>

Funcionam como cout e cin: << escreve, >> lê.

Modos de abertura. ofstream por padrão apaga o conteúdo ao abrir. O enunciado pede para adicionar ao final, então usamos ios::app (append). Sem isso, cada salvar sobrescreveria o anterior, e o exemplo do Fabio, Theo e Victor não funcionaria.

endl coloca \n e descarrega o buffer. O enunciado exige que o arquivo termine com \n, por isso cada campo é gravado com endl, inclusive o último.

Passo a passo:

Abre o arquivo em modo append (cria se não existir).
Grava os 3 campos, um por linha, na ordem do formato.
Usa os getters, pois os atributos são protected.

Por que o if (saida.fail()) return;? É uma proteção caso o arquivo não abra (sem permissão, por exemplo). O enunciado não pede tratamento, então sair silenciosamente é aceitável.

teste1: cria dois Jogador com new, cria a persistência, salva na ordem e dá delete nos dois. Regra de ouro: tudo que foi alocado com new precisa de delete.

4. Exercício 2: carregar
4.1 Estados de um stream

Todo stream tem flags:

eofbit: tentou ler além do fim do arquivo.
failbit: uma leitura falhou (formato errado ou fim do arquivo).
badbit: erro grave de I/O.

while (entrada) é verdadeiro enquanto o stream está em bom estado (sem fail nem bad).

4.2 O padrão do slide 27
lê a primeira vez
while (leitura deu certo) {
    usa os valores
    lê de novo
}

Por que ler antes do while? Se você lesse dentro do laço e usasse depois, na última volta usaria valores inválidos. Lendo ao final de cada volta, o while sempre testa a leitura que acabou de acontecer, e só entra no corpo com dados válidos.

4.3 Como o código trata cada caso
Arquivo inexistente: entrada.fail() logo após open e throw invalid_argument("Arquivo nao encontrado").
Arquivo vazio: a primeira leitura falha, o laço não executa e o vetor fica vazio. Retorna nullptr e quantidade = 0.
Arquivo bom: cada volta cria um Jogador com new e guarda no vector. Termina com eof() verdadeiro.
Erro de formato: se o laço terminou e eof() é falso, a falha foi por outro motivo (por exemplo, texto onde se esperava número). Libera os jogadores já criados e lança logic_error("Erro de leitura").

Por que deletar antes de lançar a exceção? Ao lançar, a função termina e os ponteiros do vector se perdem, causando vazamento de memória.

4.4 Vector temporário e vetor final

O retorno é Jogador** (vetor de ponteiros). Como não sabemos a quantidade de antemão, usamos um vector<Jogador*> temporário, depois alocamos new Jogador*[quantidade] e copiamos. Como o enunciado garante no máximo 10 jogadores, também seria válido alocar um vetor fixo de 10.

4.5 Exceções
invalid_argument e logic_error vêm de <stdexcept>.
No teste2, o catch (const exception& e) captura ambas e e.what() devolve a mensagem.
4.6 Posse da memória

O enunciado diz que quem chama carregar destrói os jogadores. Por isso o teste2 faz delete jogadores[i] para cada um e depois delete[] jogadores para o vetor. Note a diferença: delete para um objeto, delete[] para um vetor alocado com new[].

5. O ponto fraco (conheça antes que perguntem)

O teste !entrada.eof() detecta formato errado em que a leitura falha antes do fim do arquivo. Mas um registro cortado no final (Fabio e 10, sem a força) também termina em eof, então passa como se fosse normal.

Para entender: ao falhar numa leitura, pergunte-se se você já tinha lido parte de um registro. Se sim, o arquivo terminou no meio dele e isso é erro. Pense em como seu código poderia saber isso (por exemplo, quando cada uma das 3 leituras falha).

6. Perguntas que podem fazer, com respostas
Por que ios::app? Para não apagar os dados anteriores e adicionar ao final.
Por que ler antes do while? Para que o teste do laço sempre valide a leitura mais recente.
Por que delete antes do throw? Para evitar vazamento de memória.
Por que Jogador**? É um vetor de ponteiros para Jogador, e quem chama destrói cada um e depois o vetor.
Diferença entre delete e delete[]? O primeiro libera um objeto, o segundo um vetor criado com new[].
O que eof() indica? Que a leitura tentou passar do fim do arquivo.
Por que o hp não é salvo? O construtor o inicializa com hpMax.
Limitação do >> para o nome? Ele para no espaço, então nomes compostos não funcionam. getline resolveria.

Jogador** PersistenciaDeJogador::carregar(int &quantidade) {
    ifstream entrada;
    entrada.open(arquivo); 
        if (entrada.fail()) {
        throw invalid_argument("Arquivo nao encontrado");
    }
    
    string nome;
    int hpMax, forca;
    vector<Jogador*> tempJogadores;
    
    entrada >> nome >> hpMax >> forca;
    
    while (entrada) {
        tempJogadores.push_back(new Jogador(nome, hpMax, forca));
        entrada >> nome >> hpMax >> forca;
    }
    
    if (!entrada.eof()) {
        for (auto j : tempJogadores) {
            delete j;
        }
        entrada.close();
        throw logic_error("Erro de leitura");
    }
    
    entrada.close();
    
    if (tempJogadores.empty()) {
        quantidade = 0;
        return nullptr;
    }
    
    quantidade = tempJogadores.size();
    Jogador** vetor = new Jogador*[quantidade];
    for (int i = 0; i < quantidade; ++i) {
        vetor[i] = tempJogadores[i];
    }
    
    return vetor;
}

Copia os ponteiros do vector temporário para o vetor que será devolvido. Os objetos Jogador não são copiados, só os endereços.

cpp
    return vetor;

Devolve o vetor. A partir daqui, quem chamou é dono da memória: precisa dar delete em cada vetor[i] e depois delete[] vetor. O vector temporário se destrói sozinho ao fim da função, mas isso só libera o próprio vector, não os Jogador, que continuam vivos.

Resumo do fluxo de memória
carregar():  new Jogador (x N)  → guardados em vector → copiados para new Jogador*[N] → retornados
teste2():    delete jogadores[i] (x N)  →  delete[] jogadores

Cada new tem um delete correspondente, e cada new[] tem um delete[].

Recuo estranho: o if (entrada.fail()) está com indentação extra no seu código. Não afeta a execução, mas vale arrumar.
Registro cortado: continua sendo a única lacuna funcional, como vimos antes.
